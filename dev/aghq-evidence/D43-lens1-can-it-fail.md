## Summary verdict up front

**VERDICT: NOT-DONE.** Reason in one line: the flagship quantitative recovery
evidence (the n-ladder to 3200, the 954-fit Totoro suite that produces every
sigma/rho/runaway number in the claim) was generated by a standalone, explicitly
non-shipping R reference implementation, not by the code that ships. The link
between that reference and the real engine is validated only at toy scale (n = 3
to 30). Separately, the "eliminates the divergent-fit mode" claim is measured with
a runaway metric defined on exactly the quantity the ridge penalizes, and the
authors' own decision log shows a same-shape ridge-only control (no AGHQ) closes
most of the same gap — a fact the claim as stated to me does not carry.

## Check 1: Gaussian exactness (+6.253e-13, k-independent) — CAN it fail?

Reproduced the fixture from `tests/testthat/test-aghq-surface.R` directly (gaussian
DGP, `n_site=30`, seed 1). Baseline, unmodified code:

```
lap=45.5887409353 k3=45.5887409353 k9=45.5887409353  |k3-lap|=4.974e-14 |k9-lap|=4.974e-14
```

(Not identical to the authors' quoted `+6.253e-13` — different run/seed context, same
order of magnitude, same qualitative fact: k-independent to ~1e-14.)

Then I broke the two things this test is supposed to detect a break in, by
monkey-patching the ACTUAL adaptation function `.gllvmTMB_aghq_adapt` (the one live
on this code path — see the important caveat below about which grid function is
actually live) and re-running the same fixture:

```
=== DEFECT A: mis-centre the adaptation mode by a constant offset (0.3) ===
BROKEN(mis-centre) k3 obj=46.5660810971  |k3-lap|=9.773e-01

=== DEFECT B: wrong logdet sign (use +sum(log(diag(R))) instead of -sum(...)) ===
BROKEN(logdet sign) k3 obj=-44.9983280383  |k3-lap|=9.059e+01
```

Both defects blow through the shipped test's `tolerance = 1e-8` by 7-9 orders of
magnitude. **This is a real, load-bearing test for the code path it actually
exercises** — it is not tautological.

**Important caveat, found only by trying to break the wrong function first.** My
first defect attempt patched `.gllvmTMB_aghq_grid()` in `R/fit-multi.R` (removing
the `u^2` adaptive correction, turning the weights into plain non-adaptive GH). It
had **zero effect** on the fit — not because the defect was benign, but because
that function is **dead code at runtime**. `R/fit-multi.R` (~line 5057) prefers a
peer-supplied `.aghq_grid()` from `R/aghq-control.R` whenever it exists and passes
a sanity gate `.gllvmTMB_aghq_grid_ok()`. Since both files load together, the grid
actually used by every fit in this build is `.aghq_grid()`, and
`.gllvmTMB_aghq_grid()` is silently shadowed. This is worth naming even though it
is not itself a correctness bug (I confirmed `.aghq_grid()`, the live one, is
correct and its own defect-injections fail hard — see Check 2's oracle numbers).
It is a real risk for future maintenance: two independently-authored, near-
duplicate grid implementations exist, one of them inert, and nothing in the test
suite would notice if the *live* one silently changed behaviour in a way that
still passed `.gllvmTMB_aghq_grid_ok()` (see next paragraph).

I checked the power of that sanity gate directly:

```
original grid passes ok-check: TRUE
u^2-stripped grid passes ok-check: FALSE
permuted-nodes grid passes ok-check: TRUE   <-- d=1, k=3, reversed node order
unscaled(no sqrt2)-nodes grid passes ok-check: FALSE
random-permuted d=2,k=3 grid passes ok-check: FALSE
```

The gate catches real corruption in 4 of 5 tries. The one miss (d=1, k=3, reversed
node order) is a narrow artefact of Gauss-Hermite node/weight symmetry (w(z) =
w(-z) at this small, symmetric grid), not a generic hole — a genuinely random
node/weight misalignment at d=2 was caught. Low severity, but real: the gate is
not a universal correctness proof, and neither is downstream exactness (I directly
verified a structured-reversal defect at d=1,k=3 leaves the gaussian-exactness
number completely unchanged: `PERM-DEFECT k3 obj=45.5887409353 |diff|=4.974e-14`).

## Check 2: oracle independence (1.2e-09 claim) — is it genuinely separate code?

`dev/aghq-r-reference.R` is a from-scratch R re-implementation: its own Newton
mode-finder with backtracking, its own logit/softplus density code, its own
log-sum-exp assembly. It does not call into `src/gllvmTMB.cpp` or
`R/fit-multi.R`. It DOES reuse the same textbook Golub-Welsch construction for
1-D Gauss-Hermite nodes as the package's own grid code — but that piece is
validated independently by a moment self-test (`.aghq_grid_selftest()` /
`.gllvmTMB_aghq_grid_ok()`), not by the density/mode-finding/assembly code that is
actually what could be wrong. I re-ran `dev/aghq-evidence/02-template-vs-oracle.R`
with full precision printed (was only 4 decimals in the checked-in script output):

```
k=1  template obj 7.977968095529 | oracle 7.977968095231 | GAP +2.9729e-10 | aghq$used=FALSE
k=3  template obj 7.977968094996 | oracle 7.977968094996 | GAP +7.9936e-15 | aghq$used=TRUE
k=9  template obj 7.977968094996 | oracle 7.977968094996 | GAP +1.0658e-14 | aghq$used=TRUE
k=25 template obj 7.977968094996 | oracle 7.977968094996 | GAP +0.0000e+00 | aghq$used=TRUE
```

This is a clean, non-vacuous signature: Laplace (`aghq$used=FALSE`) shows a real,
non-zero ~3e-10 gap to an independent oracle; turning AGHQ on collapses the gap
~30,000-fold to machine precision. A vacuous/shared-code comparison would not
produce a before/after step at exactly the point where `aghq$used` flips.

## Check 4: the ridge's runaway elimination (13% -> 0%) — is it circular?

**Yes, close to circular, and the authors' own decision log already found this and
then re-litigated it.** `runaway` is defined (`dev/aghq-evidence/totoro-suite.R`,
confirmed in `R/fit-multi.R`'s comment block ~line 4855) as
`||Lambda_hat||_F / ||Lambda_true||_F > 2`. The ridge is
`0.5 * sum(loadings^2) / tau^2` — an L2 penalty directly on the loadings whose norm
defines "runaway." An L2 penalty suppressing large values of the exact quantity a
threshold-on-magnitude metric flags is not an independent finding; it is close to
what the penalty is built to do.

`docs/dev-log/decisions.md` (2026-07-28, "The fair four-arm comparison — and a
correction to my own claim", followed by "Correction to the correction") already
walks through this: a `Laplace + ridge` control (same penalty, no AGHQ) recovers
most of the small-n sigma gain and is reported as **better** than `AGHQ + ridge` on
rho at n=100/200 (0.223 vs 0.230; 0.204 vs 0.225 in their numbers). I independently
reconstructed the same four-arm split from the raw `totoro-suite-inc.csv`
(`k=1`&`tau=Inf` = Laplace+none, `k=1`&`tau=2` = Laplace+ridge, `k=9`&`tau=Inf` =
AGHQ+none, `k=9`&`tau=2` = AGHQ+ridge — the file does contain all four, though the
in-code comment table only prints three per row):

```
n = 100   Laplace+none 0.263/0.335   Laplace+ridge 0.175/0.274   AGHQ+none 0.297/0.285   AGHQ+ridge 0.194/0.280
n = 1600  Laplace+none 0.120/0.107   Laplace+ridge 0.136/0.122   AGHQ+none 0.050/0.075   AGHQ+ridge 0.048/0.072
```
(sigma error `|sigma_rat-1|` / rho error `rho_absd`, my own aggregation, not exact
copies of the authors' numbers — different aggregator, roughly the same shape)

My reconstruction agrees on the qualitative point that matters here: **at n=100 the
ridge does most of the work regardless of which engine it is attached to**, and
AGHQ's distinguishable marginal contribution grows only at large n (n=1600, where
`AGHQ+none` already beats `Laplace+ridge` outright — the quadrature, not the
penalty, is what is buying that cell). The claim under review states "it also
recovers ... BETTER than Laplace at every sample size tested" without this
attribution — a reader would credit AGHQ for a small-n effect that is
substantially the ridge's, exactly the concern this check exists to probe for.
This is not a fabricated concern; it is the authors' own finding, just not
propagated into the claim as stated to me.

## Check 5: the 954-fit Totoro table — paired, same DGP, selected on outcome?

Read `dev/aghq-evidence/totoro-suite.R` directly. **Paired: yes** — `d <- mk(...)`
is drawn once per `(n,p,q,seed)` grid row, and both `k` values (and both `tau`
values, run as separate grid rows sharing the same seed) refit the *same* `d$Y`
against the *same* `d$Lt`. Confirmed empirically: 30 distinct seeds per `(n,
engine)` cell, matching the "30 seeds/cell" claim, once you account for Laplace's
`k=1` rows being recorded once under each `tau` setting (60 raw rows / 30 distinct
seeds).

**Selected on outcome: partially, and this is the more consequential finding of
this check.** The single biggest thing I found while trying to reproduce the
headline table is:

**The 954-fit campaign that produces every sigma/rho/runaway number in the claim
does not call the package.** `grep -c "gllvmTMB(" dev/aghq-evidence/*.R` shows only
`01-laplace-error-regime.R` and `02-template-vs-oracle.R` (both toy models, n <=
30) call the real `gllvmTMB()`. Every other evidence script — `03` through `16`,
and `totoro-suite.R` itself, including the n=3200 descent
(`05-descend-from-large-n.R`) — sources `dev/aghq-r-reference.R` instead. That
file's own header says: *"It is NOT a shipping route and must never become one: it
duplicates one family in R, which is precisely the drift risk the template design
exists to avoid."* The reference implementation has its own Newton mode-finder,
its own ridge application (`fn <- function(par) { v <- ref_nll(...); v +
0.5*sum(par[-seq_len(p)]^2)/tau^2 }`), and none of the shipped engine's outer
machinery — no multi-start, no iterative re-adaptation-to-convergence loop, no
per-(family,tier) optimizer table, no node-count ladder climb. The link between
this reference and the real template is validated ONLY at n = 3 to 30 sites
(Golden 1/2, `02-template-vs-oracle.R`) — never at the n = 100 to 3200 scale where
every headline recovery number in the claim actually lives.

I ran one cell of the real campaign through the actual shipped engine myself, to
see whether the qualitative story survives contact with the product (same DGP
generator copied verbatim from `totoro-suite.R::mk()`, n=100, p=6, q=2, seed=1001,
`gllvmTMB(..., control = gllvmTMBcontrol(aghq = 9L, aghq_ridge = 2))`):

```
Laplace:     frob_rat=11.393  sigma_rat=0.473  rho_absd=0.507  conv=0
AGHQ+ridge:  frob_rat=1.098   sigma_rat=1.139   rho_absd=0.192  conv=0   (aghq$used=TRUE, passes=14)
```

This is reassuring as far as it goes — a severe real-engine Laplace runaway
(11.4x!) is genuinely fixed by the real AGHQ+ridge path (down to 1.1x), and rho
error drops by more than half. But it is one seed, hand-run under time pressure,
not the systematic 30-seed check the claim implies. Each real-engine AGHQ fit
costs 30-150 seconds even at `n_init=1`/no multistart (measured from
`dev/aghq-h2h-new.rds`: 90-145s per fit), so a full real-engine repeat of the
954-fit table is expensive but not infeasible — it has simply not been done. **No
one has checked whether the actual product reproduces the specific numbers in the
claim at realistic scale**; they have checked that a different, admittedly
closely-related, but explicitly non-shipping program does.

Outcome-selection in the data itself: I could not exactly reproduce the headline
table's numbers (e.g. "Laplace, n=100, runaway=50%") from the checked-in
`totoro-suite-inc.csv` under several reasonable reconstructions (all fits vs
`conv==0`-only, pooling both DGP shapes vs restricting to p=6/q=2) — I got 8-25%
depending on filter, never 50%. This may be a stale/superseded CSV, a different
convergence-filter convention than I guessed, or a genuine discrepancy; I flag it
as **unresolved** rather than asserting the headline table is wrong, but it means
I could not independently confirm the exact reported magnitudes, only the
qualitative direction and the four-arm attribution point above.
